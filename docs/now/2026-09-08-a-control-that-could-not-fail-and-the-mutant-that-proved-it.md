# NOW -- A control that could not fail, and the mutant that proved it (2026-09-08)

## A control that could not fail, and the mutant that proved it (Closes #3436)

- `gen-rust` passes a struct parameter by value, so a non-`Copy` struct is MOVED into the call and a caller reading the same value twice does not compile. The derive asked a helper that knows the scalars and `[T; N]` and nothing about declared types, so `struct Outer { i : Inner }` lost `Copy` even though `Inner` had it -- `error[E0382]: use of moved value`. Enums were the second half: every enum is emitted `Copy` unconditionally, yet an enum-typed field still disqualified its owner.
- Measured over 582 translation units, before against after: `error[E0382]` **125 -> 106**, files carrying one **27 -> 21**, total errors **3251 -> 3223**, files that compile **370 -> 372**. Population: 1034 structs, 579 without `Copy`, **24 in 18 files** qualify once transitivity is applied.
- Exactly one class grew, `E0119` 6 -> 7, and it is not this change: `specs/ml/optimizer/adamw.t27` emits `AdamWConfig` twice -- the struct is not declared in that spec at all, it arrives through `use` -- so a third derived trait yields a third conflict. That file fails either way. Filed separately.
- **The negative test could not fail.** A mutant admitting EVERY struct to the fixpoint passed all five tests, because the derive asks about a FIELD's type (`Vec<u8>`) and never about `Bag`'s own name; the mutant stayed invisible until a struct was given `Bag` as a field. The test now nests the un-copyable struct inside another and hands the result to `rustc`, because `#[derive(Copy)]` on a struct reaching a `Vec` is itself an error. Three mutants, three dead.
- Two instruments of mine hid data behind an unmarked slice in the same pass: `check_ring_spec_drift.py` printed `differing 7` above six names (`diff[:6]`), and a measuring script capped a field list at five so `MemDesc`'s `[MemPort; 8]` -- the actual cause -- never appeared. The cap is removed from the tool that ships.
