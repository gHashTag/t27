# NOW -- layer_sequencer runs forever on a zero count (2026-08-21)

## fix(bitnet): guard both zero counts in layer_sequencer RUN (Closes #1977)

- **The defect is live on `origin/master` verbatim, and the issue understates it.** #1977 reports one runaway (`num_neurons == 0`) and says the sibling case is already handled: "`layer_sequencer` already contained `if (num_chunks == 0) state <= DONE_ST` and had simply not done the same for neurons". It does not. `bootstrap/src/bitnet_pipeline.rs:162` on master emits `if(chunk_id==num_chunks-1) begin chunk_id<=0;` with no zero guard anywhere in the module. **Both** counts run away, not one. The issue's fixes were landed on a branch that never merged, so it reports itself as fixed while master still emits the original text
- **Why the terminators cannot match.** Both are `== count-1` compares, and the literal `1` widens each subtraction to 32 bits, so a zero count borrows to `32'hFFFFFFFF` while the index zero-extends. `neuron_id==num_neurons-1` and `chunk_id==num_chunks-1` then never match *whatever the index counts up to* -- this is worse than an 8-bit wrap, which would at least have terminated the chunk loop after 256 beats
- **Fix**: one guard at the top of `RUN`, `if(num_neurons==0 || num_chunks==0) begin valid<=0; state<=DONE_ST; end`, with the existing body moved into the `else`. Zero neurons or zero chunks is zero work, so the FSM retires with `valid` low, which is what keeps the safety bound `valid |-> neuron_id < num_neurons && chunk_id < num_chunks` true
- **Measured on the emitted RTL with `iverilog`.** Old: no `done` within **200,000 cycles** for `num_neurons=0` (199,999 valid beats, `neuron_id` reached **49,999** for a request of zero) and likewise for `num_chunks=0` (`chunk_id` sweeping the full 0..255 range forever). New: `done` in **4 cycles**, **0 valid beats**, for all three of `(0,4)`, `(4,0)`, `(0,0)`
- **Nothing traded away.** Six non-zero controls -- `(1,1) (4,4) (3,7) (5,3) (1,255) (100,2)` -- are byte-identical between old and new emitter on cycle count, valid-beat count, max index and an order-sensitive signature over the whole `(neuron_id, chunk_id, first_chunk, last_chunk)` stream
- **Three guards, three separate mutants**, because assertions abort in order and one mutant per file would leave the later ones unproven. Dropping `num_neurons==0` fails only `sequencer_run_guards_zero_neurons` (29 pass, 1 fail) and hangs only the neuron case; dropping `num_chunks==0` fails only `sequencer_run_guards_zero_chunks` and hangs only the chunk case; demoting the guard below the compares fails only `sequencer_zero_guard_dominates_the_compares`
- **The existing suite was blind to this.** Restoring master's `RUN` block under the new tests reproduces master's emitted RTL byte-for-byte, and all **27** pre-existing tests still pass on it while all 3 new tests fail. `sequencer_idle_arms_on_start` is the text-pinning test #1977 names -- it pins `IDLE: begin done<=0;`, which this change does not touch
- Adjacent, **deliberately not fixed here** and filed separately: `first_chunk`/`last_chunk` are not cleared in the reset branch, the `case(state)` has no `default:` arm, and `valid` is asserted one cycle after the `(neuron_id, chunk_id)` it labels. None of them is the zero-count defect and none is needed to prove it
