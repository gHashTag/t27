# `coq/Kernel/PhiFloat.v`: two inductives named `binary_float`, and three defects behind the first one

- Diagnosed the step-5 failure of `Coq kernel` run 32475226437 (the first run ever to get past step 4, after #2320). Flocq 4.2.2 declares **two distinct inductives both named `binary_float`** with identical constructor and projection names: `IEEE754.Binary` (NaN carries a payload) and `IEEE754.BinarySingleNaN` (one payload-free `B754_nan`).
- Established which `binary64` was in scope: `IEEE754.Bits` closes `Section Binary_Bits` (`Bits.v:613`), ending its local `Notation binary_float := (binary_float prec emax)`, and only then writes `Definition binary64 := binary_float 53 1024` at `Bits.v:687` — where bare `binary_float` is **`Binary`'s**, since Bits imports Core, BinarySingleNaN, Binary in that order. Confirmed independently by `b64_opp := Bopp 53 1024 unop_nan_pl64`, which passes a NaN-payload function that only `Binary.Bopp` takes.
- So `binary64` was fine and transparent; the mismatch was on the other side. `Import Binary Bits BinarySingleNaN.` put BinarySingleNaN last, so bare `B2R` (and `B754_finite`) resolved to **BinarySingleNaN's**. Both types print as `binary_float 53 1024`, which is why a plain name-resolution bug read as a `Definition` refusing to delta-unfold.
- Fixed by module-qualifying every colliding name — `Binary.B2R`, `Binary.B754_finite`, `Binary.B2FF`, `SpecFloat.bounded`, `BinarySingleNaN.mode_NE` — and deleting the blanket `Import`. Reordering it would also compile and would silently mean a different type, so qualification is the fix, not the ordering.
- Three further defects, none previously observable because steps 5-9 have never executed: (a) `bounded` is a section-local `Notation` in both Flocq modules and exported by neither — the real constant is `Coq.Floats.SpecFloat.bounded`, now `Require`d and named explicitly; (b) `Open Scope Z_scope.` sat *after* `Open Scope R_scope.`, so `<` and `-` resolved to `Z.lt`/`Z.sub` and `Rabs _ < _`, `0 < phi_tolerance`, `0 < PHI_F64_TOLERANCE` were three type errors with no float content; (c) `phi_sq_f64 = phi_plus_one_f64` was proved by `vm_compute. reflexivity.`, which cannot work — `Bmult` builds its certificate from `Bmult_correct_aux` and `Bplus` from `binary_round_correct`, both `Qed`-opaque, so the two terms have identical data and non-convertible proof components, and `Prop` has no definitional proof irrelevance.
- Kept the claim at full strength: bit-identity is now stated on `full_float` (`Binary.B2FF` erases the `bounded _ _ = true` certificate, so `vm_compute` decides it) and the original structural equality is recovered via `Binary.B2FF_inj`, whose entire content is that erasure step. `phi_identity_contract` keeps its statement and its proof script verbatim.
- Verified the arithmetic independently of Coq: φ's nearest double is `7286977268806824 * 2^-52` (`0x3FF9E3779B97F4A8`), `1.0` is `4503599627370496 * 2^-52`, and `fl(φ*φ)` and `fl(φ+1)` are bit-identical at `5895288448088660 * 2^-51` (`0x4004F1BBCDCBFA54`) — matching `scripts/validate_phi_f64.py`. The residual is exactly zero, so nothing had to be weakened.
- Not weakened: no `Admitted`, `admit`, `Axiom`, `Parameter` or `Local Set`, and no lemma dropped, so step 9 (`Verify Kernel PHI layer has no Admitted`) stays meaningful.
- **Measured, not asserted.** This was not compiled locally — opam, Flocq and the container are unavailable in that environment. CI is the verification, and run 32477122735 on the branch reports step 5 `Build coq/ (T27 + Flocq)` **success** and step 6 `coqchk PhiFloat (consistency)` **success**: the whole file elaborates and the kernel re-checks it. Steps 5 and 6 had never once succeeded before.
- That run then reached step 8 and exposed the next never-executed defect: the step ran `t27c validate-phi`, a subcommand that has never existed (`error: unrecognized subcommand 'validate-phi'`, exit 2). The real one is `validate-phi-identity` (`bootstrap/src/main.rs:1656`).
- Pointed step 8 at `validate-phi-identity` **and renamed the step** from `Build t27c and validate phi f64 parameters` to `Build t27c and validate the L5 phi identity`, because that subcommand checks `phi^2 + phi^-2 = 3` in f64 — not the binary64 mantissa/exponent literals the old name promised. `scripts/validate_phi_f64.py` prints those parameters but never reads `PhiFloat.v`, asserts nothing about it and always exits 0, so no gate compares the two. Renaming down to the weaker check rather than letting the old name launder it; the missing comparison is #2324.
