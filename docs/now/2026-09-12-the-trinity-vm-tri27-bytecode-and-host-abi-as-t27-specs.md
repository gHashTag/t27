# NOW -- The Trinity VM, the TRI-27 bytecode and the host ABI as .t27 specs (2026-09-12)

## S05 of gHashTag/trinity#988: the machine the consumer actually runs, rule by rule (Closes #3567)

- Three files state the TRI-27 layer of gHashTag/trinity at `976df517` as its tests execute it, not as its documents describe it. `specs/isa/ternary_encoding.t27` (module `Tri27Encoding`, `KIND = "isa-encoding"`, rewritten: until today a 38-line block that did not parse and was the canonical spec of the whole toolchain) is the instruction word of `src/tri27/emu/decoder.zig`: the forty-seven opcodes with their values, the three field layouts, the fifteen-bit immediate and its sign extension, the four-bit `src1` of the immediate form, the unknown-opcode-is-NOP rule, and two rules the owner never wrote down -- `DOT`, `BIND`, `BUNDLE2` cannot carry `src2` (it decodes as `t0`) and `SACR` cannot carry its mode (every decoded `SACR` adds). `specs/isa/tri27_machine.t27` (`Tri27Machine`, `KIND = "isa-machine"`) is `executor.zig` with `cpu_state.zig`: 27 i64 registers, 19683 eight-byte words read four bytes at a time at `pc * 4`, two entry profiles (`pc 3, sp 0` by `CPUState.init` and memcpy, the path of every owner test and of `tri tri27 run`; `pc 0, sp 19682` by `loader.load`), four flag bits with `V` never written, the numeric rule of every executed opcode (no reduction for `ADD`..`DEC`, modulo 3^9 = 19683 for `DOT`, `BIND` and `SACR`, fixed-point series for `EXP` and `SIN`), the stack, the 100000-instruction budget that halts silently, the seven declared errors of which two are never returned, twelve status codes of the spec's own (the owner has no ordinals), the exit codes of the `tri` process, and the host boundary: `SYSCALL` is a no-op and file and string I/O are opcodes that open paths from guest memory unsandboxed. `specs/isa/tri27_bytecode.t27` (`Tri27Bytecode`, `KIND = "isa-bytecode"`) is the `.tbin` container of `loader.zig`: the six-byte header, the four section kinds, every rejection (truncated, wrong magic, unsupported version, unknown section, code that does not fit, no code) in the order the loader decides them, and where the code lands.
- Fifteen, eight and six findings are recorded, not inherited. The two that decide the most: `CALL` pushes its own address and `RET` returns to it, so every subroutine call is an endless loop stopped by the budget (no owner test executes a `CALL`); and `loader.load` writes code into eight-byte words while `run` fetches four-byte units, and reads a `tri_asm.zig` container two bytes early, so nothing the loader loads runs as written -- the owner's golden tests never use it. Also: `MEM_SIZE` and `3^27` labels that are 27 and 3^9, five incompatible instruction layouts across the documents and the emitters, an assembler behind `tri tri27 assemble` whose words the decoder misreads, a `validate` that prints not-implemented and records success, `InvalidMemory` unreachable from any encodable load or store, the `CONSTANTS` section whose id byte is read as its count.
- `tools/trinity_tri27.py vectors` assembles twenty-two programs in the decoder's layout and runs them through a Python model of the three files, and writes `conformance/trinity/tri27_programs.json` with every program's words, container, final registers, flags, memory changes, status and a bounded trace (32 steps), plus eighteen loader vectors -- one per rejection rule and per accepted shape. Eight programs end with a nonzero status: an invalid register (refused before it counts), an invalid opcode (`ADD3`), division by zero, the stack guard after `loader.load`, a fetch past memory, `RET` on an empty stack, the budget, and host I/O (not replayed). `run` generates the three specs to C with `t27c gen-c`, links them into a driver that owns the arrays and the loops and calls the specs for every decision, and replays: 40 of 40 pass, traces included. `check` holds the record to the specs and the model; `--self-check` plants a wrong register, a rejection declared as acceptance, a `BIND` without its zero identity (fails only the vector that binds a zero to a negative value) and a wrong sign bit (fails only the negative-immediate vectors).
- `specs/vm/trinity_vm.t27` (`TrinityVsaVm`, `KIND = "vm-contract"`) is the other VM, `src/vm.zig`: twenty-six opcodes numbered by declaration order, four hyperdimensional registers over S04's operations, a register index above 3 that aliases `v0`, condition codes at a tenth, no budget, no serialized form, forty sacred opcodes of which six are implemented and reachable only outside the instruction path. Its CI evidence is recorded as it is: `zig test src/vm.zig` fails to compile on every push to main (run 34678824259). `specs/server/vm.t27` names the same VM without numbers and does not parse; it is cited.
- `specs/api/c_abi.t27` (`TrinityCAbi`, `KIND = "host-abi"`) is the C boundary, `src/c_api.zig`: twenty-two exports with their prototypes, ownership (every handle the caller frees, two caller buffers, one static string) and NULL rules, no error channel, an opaque handle over a struct that is not ABI-stable. `tools/trinity_c_abi.py check --trinity-root` holds the table to the header and to the `export fn` lines (names, arity, prototypes: all twenty-two agree), compiles the fixture `conformance/trinity/abi/abi_fixture.c` against the header (it compiles) and, given a zig, records that `zig ast-check` rejects the source at the pin -- a duplicated `if` in `trinity_vsa_set_trit` -- so neither the library nor its fifteen tests build. Not linked, not run; the S01 card stays `declared`.
- The S01 cards `abi.c-api`, `tri27.toolchain` and `lib.trinity` now name their canonical specs; `specs/OWNERS.md` gains rows for `vm/` and `api/` and extends `isa/`; `tools/specs_generate_baseline.txt` loses the encoding stub (it generates now); `tools/published_figures.py` pins move by the corpus: test blocks 12673 -> 12709, `pub const OP_*` 11 -> 60.
- Not claimed: that any of this ran on the owner's Zig (no build target, standalone binaries that do not compile, no Zig on this host that builds the tree); that the string and file opcodes, `cpu.f`, the vector registers or `SACR` modes 2..4 are replayed; that the VSA VM's programs are replayed (its operations are S04's vectors); or that the C ABI is verified across a linked boundary. Hardware is not involved anywhere in S05; every result here is emulation of a specification and is labeled so.
