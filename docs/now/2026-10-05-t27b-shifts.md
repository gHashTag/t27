# NOW -- t27b shifts follow the Zig backend (2026-10-05)

## Integer `<<` and `>>` in t27b, untyped literal on the left (Closes #6288)

- t27b already lowered typed shifts: LSLV/ASRV/LSRV for a runtime amount, which traps (`ShiftRange`) when the amount is outside 0..bits as Zig's `@intCast` panics, and the lsl/asr/lsr immediates for a constant one. `>>` is ASR on signed types and LSR on unsigned ones. The one missing shape was an untyped literal shifted by a non-literal amount (`1 << n`), the first rejection in 36 corpus files.
- t27b now mirrors compiler.rs `shift_runtime_rhs`: such a literal is pinned to the declared integer type of the local it initializes, else to u32 (u64 when it does not fit). A constant amount out of range for that type is refused by name (a Zig compile error there), never masked. Constant-on-both-sides typed shifts fold in the operand's type, dropping bits as Zig's `<<` does.
- t27c folds literal-only trees and propagates literal local consts before gen, but only in some positions of a function body. When a literal-only amount gives a different value folded (comptime_int) than pinned, t27b refuses with "untyped literal shift whose width depends on t27c constant folding" instead of guessing (`0xFF << (20 + 8)` returns 0xFF0000000 in the reference, but 0xF0000000 if pinned).
- Tests: encoder rows for LSLV/LSRV/ASRV in both widths and the lsl/lsr immediates against clang words; differential `shift_source_programs_run_in_both_engines` (same verdicts as `t27c test-report`: 1 pass, 3 ShiftRange traps) and `shift_refusals_name_the_construct`.
- `t27b corpus specs`: pass 191 -> 223, pass_vacuous 279 -> 279, fail 3 -> 3, rejected 743 -> 711, JIT/interpreter mismatch 0. All 32 newly passing files pass under `t27c test-report` with the same test counts.
- Not done: `<<=` / `>>=` do not parse in t27c ("Unexpected token in expression: Equals"), so there is nothing to lower for them.
