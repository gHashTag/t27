# NOW -- interrupt_controller: the clear was the last write, so it won every time (2026-08-21)

## W555's lost-interrupt race lands on master, and the tests that held it in place are replaced (Closes #1967)

- The defect was reported fixed in Wave Loop 555 on 2026-08-08. It was **never on `master`**. `bootstrap/src/bitnet_irq.rs` at `fead099c2` still emitted the racy chain verbatim at lines 100-103, and `bootstrap/src/main.rs:4419` still shipped it through `t27c gen-interrupt-controller`. The campaign's fix commits are on a branch that diverged (`ahead=784, behind=2419`) and carry no PR, so every consumer of this emitter has been generating the broken RTL for the two weeks since
- **The defect.** Three sources and a read-clear were four independent non-blocking assignments in one `always` block. NBAs in one block resolve last-write-wins, so `if (status_read) irq_status <= 3'b000;` -- written last -- beat all three sources unconditionally. A host acknowledging an interrupt discarded any event raised in the same cycle as its status read
- **Reproduced before fixing, not taken on the issue's word.** Both emitters were built, their Verilog diffed, and old and new instantiated side by side in one iverilog testbench driven from the same stimulus. Event concurrent with read: `old irq_status=000`, `new irq_status=001`. The event is not at risk on the old design, it is *gone*
- **No behaviour traded away.** Same bench, two control cases: read-to-clear with no concurrent event still clears (`old=000 new=000`), and the latch is still sticky across idle cycles (`old=010 new=010`). The fix is `irq_status <= (status_read ? 3'b000 : irq_status) | {error, dma_done, inference_done}` -- clear the previous value, OR this cycle's sources on top. Yosys lowers it to one `$adff` plus a mux and an or; the priority chain is gone rather than reordered
- **Two unit tests and two integration tests were pinning the bug in place.** `each_source_latches_its_bit` and `status_read_clears_latch` asserted the *literal text* of the racy chain, in `bootstrap/src/bitnet_irq.rs` and again in `bootstrap/tests/bitnet_irq.rs`. They passed for exactly as long as the race existed and would have failed the moment anyone repaired it -- the wrong way round. A test that asserts the shape of an implementation cannot notice the implementation is wrong
- **What replaces them is structural, not textual.** `count_irq_status_nba` counts non-blocking drivers of `irq_status`, split into reset arm and update arm, and the update arm must be exactly **one**. That is the defect *class* -- more than one driver in one clocked block -- so a reintroduction under different formatting, different guards, or a different spelling is still caught, where four `contains()` calls would not be
- **The counter carries its own negative control.** `driver_count_sees_the_historical_race` feeds it the pre-fix block and requires the answer `4`. Without that, a counter that always returned `1` would pass the racy design just as happily as the fixed one, and the gate would be decorative. Checked by construction: the new tests were run against the *unfixed* emitter and 4 of them fail, the driver count reporting `left: 4, right: 1`
- **Scope held.** `bitnet_top.rs` ties `status_read(1'b0)`, so the race cannot manifest at that integration level and no wiring changed. `host/mmio.rs` models read-to-clear and stays correct -- it is untimed, so it cannot raise an event concurrently with a read in either direction; its comment now says so, and its stale `around line 103` pointer is replaced by a function name
- Nothing else from the wave-547 campaign is ported here. This is one defect, one file's emitter, and the four tests that were guarding the wrong thing
