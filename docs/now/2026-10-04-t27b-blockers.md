# NOW -- t27b corpus --blockers names every construct a spec needs (2026-10-04)

The t27b corpus run reported only the first construct that stopped each spec.
That shows what blocks a file, not what it takes to pass it.

## Blockers and the greedy order (Refs #5977)

- `t27b corpus <dir> --blockers` keeps lowering after a rejection and lists
  every unsupported construct per file, once per kind. A rejected expression
  becomes poison, so one missing construct is not reported again for each use.
- The run prints a greedy set-cover order. Each step picks the construct
  that lets the most whole files pass.
- On master, 1129 of 1185 files are blocked by 169 distinct constructs. A
  file needs between 1 and 35 of them, with a median of 5.
- The first steps are `ExprCast` (+18 files), `1 << n` (+27),
  `assert(c, "message")` (+18), `struct` (+17), `invariant` (+14) and more than
  8 parameters (+12). `ExprArrayLiteral` completes 333 files at step 26.
- `--reference <t27c>` runs `t27c test-report` (gen + zig test) on each file
  and counts the files the reference fails separately, so a spec that does not
  compile through Zig is not counted as a t27b gap. `--reference-cache` keeps
  those results between runs.
- The corpus count is unchanged at 36 passing, 0 failing and 0
  JIT/interpreter mismatches. The differential test still reports 0 mismatches.
