# NOW -- The string that looked like a number (2026-09-08)

## The string that looked like a number (Refs #3459)

- The largest error class had 1401 left after the previous pass, all one shape: a bare list of numeric literals, carrying a type nowhere. Rust writes `let mut x = [1, 2, 3]` and Zig `var x = .{ 1, 2, 3 }`; only C has no inference for a brace list, so the type must be NAMED. The choice is not arbitrary -- it matches what a scalar literal already gets, `uint32_t x = 1` here and `var x: u32 = 1` in Zig -- and any fractional element makes the list `double`, which is C's own promotion.
- Measured: errors **14738 → 14276**, the class **1401 → 837**, **31 files better**. `igla/race/ternary_gemm` 437 → 348, `igla/race/rtl` 268 → 197.
- **The corpus refuted my first version.** A STRING literal is an `ExprLiteral` whose `value` is the text WITHOUT its quotes, so `["12", "34"]` passed a digit test and the list was typed `uint32_t`: four «incompatible pointer to integer conversion initializing 'uint32_t' … with an expression of type 'char *'» in one file. Excluding `extra_kind == "string"` fixed it, and the per-file check is the only reason it was seen -- the aggregate had improved either way.
- Two files still rise and both are unmasking, checked one at a time rather than generalised: an unnamed tuple struct losing `f0`, and `member reference base type 'int'`. A third, a `uint16_t` field initialised from a `uint32_t[4]`, was wrong before and had no type to be wrong against.
- **A speculation was reverted with its reason recorded.** A ONE-element literal `[7]` arrives as an `ExprArrayLiteral` with ZERO children -- confirmed by instrumenting the branch -- while the emitted C still reads `{ 7 }`, so the element is kept somewhere this code does not read. `lit.value` was the obvious candidate, was tried, and is empty too. 334 of the remaining 837 are `{ 0 }` and every one takes that path. Filed rather than guessed at.
- A mutant survived on a guard that is SUBSUMED rather than unreachable: deleting `kind != ExprLiteral` changes nothing, because an identifier, a call and a binary expression all reach the value checks with nothing numeric to offer -- probed, all three. It stays, and the difference from the `has_init` parameter deleted last pass is written down: that one no caller could reach; this one is reachable and dropping it would make correctness depend on an accident.
