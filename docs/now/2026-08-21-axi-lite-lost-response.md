# NOW -- axi: a slave that accepted twelve writes and answered seven (2026-08-21)

## The lost-response defect was fixed on a branch and left live on master (Closes #1968)

- `bootstrap/src/bitnet_axi.rs` asserted `s_axi_awready`, `s_axi_wready` and `s_axi_arready` at reset and **never deasserted them anywhere** -- `s_axi_awready <= 1'b0` did not occur once in the emitted module. The module holds a single `bvalid`/`bresp` register and a single `rvalid`/`rdata`/`rresp` register, so it can owe at most one response per channel. Accepting a second transaction while the first is unacknowledged merges two transactions into one response beat, and an AXI master then waits forever for a beat nobody will send
- #1968 reported this as fixed. It was fixed on `feat/wave-547/host-heapsort`, which has no PR and is 2419 behind. On `master` the defect was still there verbatim, and `master` is what `t27c gen-axi-lite-slave` and the `bitnet_bundle` emitter ship
- The fix is the one the formal harness proved: release `ready` only on the response handshake, drop it on accept. It costs one cycle of throughput per transaction, which is what a single-response-register design implies. `awready` and `bvalid` are now complementary by construction, so `outstanding <= 1` holds without a counter. The #925 ordering (clear before accept) is left exactly as it was
- **Measured on the emitted RTL, not argued.** Both emitters were run to Verilog and simulated under iverilog with a testbench that counts accepts against response beats -- the same quantity #1968 formalises as `outstanding_w <= 1`, not a handshake-shape check. Master's RTL: **12 write accepts, 7 B beats, max outstanding 6** -- five responses lost, and the read channel identically. Fixed RTL: 4 accepts, 4 beats, max outstanding 1 on both channels, and `reg_ctrl` still lands, so the delayed write is delayed and not dropped
- **`axi_handshake_dropbacks_present` was holding the bug in place.** In both `bootstrap/src/bitnet_axi.rs` and `bootstrap/tests/bitnet_axi.rs` it asserted the literal single-line handshake clears -- the exact form that left `ready` asserted. It passed for as long as the defect existed. A test that asserts the shape of an implementation cannot notice that the implementation is wrong
- The replacement guard is not another text pin. `axi_ready_drops_while_a_response_is_owed` asserts that each of the three ready signals has a deassertion **at all**; that is the general shape of the defect, so a reformulation passes and re-pinning any ready high fails however it is spelled. `axi_ready_release_is_tied_to_the_response_handshake` additionally requires the release to sit inside the response-handshake block and the drop inside the accept block, so a ready that is dropped and restored somewhere that does not bound the outstanding count still fails. Both added at the library and the shipped-CLI level
- **`axi_reset_initializes_all_outputs` was silently weakened by the fix and is repaired in the same commit.** It asserted `s_axi_awready <= 1'b1;` against the whole module; that string now also appears in the release block, so the test would have passed even with the line deleted from the reset branch. It now searches only the `if (!rst_n) begin` .. `end else begin` slice -- strictly stronger than before the fix
- **Negative control.** Every new assertion was run against the pre-fix emitter rebuilt from `origin/master`: `axi_ready_drops_while_a_response_is_owed` FAILS there, and the simulation FAILS four of five checks. Against the fixed emitter 19 of 19 unit tests pass and the simulation passes. A guard that only proves is not evidence that it can refute
- **What did not land, and what is still wrong.** `formal/axi_lite_slave_props.sv`, the Yosys `sat` flow and the vacuity gate described in #1968 exist only on `feat/wave-547/host-heapsort`; none of `formal/`, `formal-yosys.yml` or `docs/FORMAL_FOUNDATIONS.md` is on master, and no required check on this repo runs `cargo test`, so these tests gate nothing until one does. Separately and unchanged by this commit: the write path still requires `awvalid` and `wvalid` in the *same* cycle, so a master that presents AW and W on different cycles has its AW beat completed and discarded. That is a second, pre-existing defect in the same module; it is not what #1968 reported and is not claimed fixed here
