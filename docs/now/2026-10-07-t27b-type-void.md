# NOW -- t27b: `void` as a parameter, field and pointee type (2026-10-07)

## Zig's zero-bit `void` (Closes #7267)

- New conformance spec `specs/tri/t27b/conformance/type_void.t27`. It gives 4 pass with 0 vacuous under `t27c test-report`, and the same 4 under t27b, with 9 runtime asserts.
- Ported specs use `void` for plumbing they do not model: `alloc: void`, `p: *void`, or a struct field that holds nothing. t27b now lowers `void` outside a fn result as a struct with no fields and size 0. Its neighbours keep their own offsets, an array of structs holding one keeps its stride, and `undefined` passed for a `void` parameter is that parameter's only value. A `void` fn result still means no value.
- `?void` is refused as `type ?void`. Its only non-null value is `undefined`, which leaves the has-value flag unwritten too; a first lab run showed t27b's JIT and interpreter reading those bytes differently.
- 8 mutants: 7 fail the same tests in t27b and in the reference. One (calling a fn whose parameter is `*void` with `undefined`) runs under the reference and is refused by t27b.
- 16 probes, none disagree. 10 pass in both, and 1 fails in both. 4 pass the reference and are refused by t27b: `?void`, `==` on two `void` values, `return x` in a `void` fn, and `undefined` passed for a `u32` parameter. 1 more (`?u32` returning `undefined`) passes both but gives a JIT/interpreter mismatch in t27b, master included. The reference passes it only through Zig's Debug fill bytes; filed as #7268.
- Code is in `cli/t27b/src/lower.rs`, which is listed in `tools/policy/foreign-exceptions.txt` under the owner's approval on #6063.
- Ledger `docs/reports/t27b_expectations.json`: `specs/port/trinity/src/background_agent/main.t27` (4 pass, 6 asserts) and the new spec move to pass. `specs/port/trinity/src/tri/gen_softmax.t27` now stops at `ExprCall(@exp)`.
