## The compiler was right a fourth time (Closes #3438)

- I filed #3438 as «a type pulled in through `use` is emitted twice». Both halves were wrong and I wrote them. `AdamWConfig` is not imported: `specs/ml/optimizer/adamw.t27` declares it **itself, twice**, at lines 28 and 483, and the two bodies are not identical -- one ends `use_phi_betas : bool`, the other `phi_variant : PhiVariant`. My original grep looked for `struct AdamWConfig` and the spec uses the Zig spelling `pub const Name = struct { … }`; finding zero, I concluded it must be imported. `use_resolve.rs` emits nothing twice. The compiler is right and the spec is wrong -- the fourth time this campaign, after #3420, #3422 and #3428.
- The real defect is that **`t27c check` exits 0** on it, while every backend it compiles to rejects a redeclaration. Measured against the real compilers rather than assumed: `cc` says `redefinition of 'S'`, `rustc` `error[E0428]`, `zig` `duplicate ...`, `iverilog` `has already been declared in this scope`.
- **Two findings, not one, because one message would be false for half the cases.** `struct A` + `fn A` is ACCEPTED by rust and by C -- types and values are separate namespaces there -- and rejected by zig, which gives a container one namespace. So the strong message is reserved for a same-namespace collision and the cross-namespace case gets its own, weaker, true one. The corpus carries **0** of the weak kind, and that zero is only worth printing because a control proves the message is reachable.
- Population, from the compiler's own AST: **3 specs, 25 names** -- and it agrees exactly with an independent count taken from the generated Rust two passes ago. A line-based matcher I wrote while scoping said 8 specs and 35 names; five of the eight were its own false positives, `impl`-block methods in files written in Rust that do not parse and emit **0 bytes**. Scope is not visible to a regex, which is why the detector walks the AST.
- Corpus effect measured spec by spec, old binary against new: 651 specs, exit codes **573 zero and 78 one before and after, and not one spec moved**. Wired into `Spec Guards` as a per-spec ratchet, 7s, with a self-check that requires the planted duplicate to be found AND the clean spec to stay quiet AND the cross-namespace case to take the weaker message. Three controls on the gate itself: a new spec turns it red, a baselined spec that grows turns it red, a shrink is reported as progress and passes.
