# NOW -- t27b compiles []T slices (2026-10-05)

## Slices: params, a[i..j], a[i..], .len, checked index, for (Closes #6248)

- `[]T` and `[]const T` (any element t27b already has; `[]const u8` stays `str`) lower to a 16-byte (ptr, len) header in memory, passed by reference like a struct. Coercions follow Zig: `*[N]T` to `[]T`, `*const [N]T` and `[]T` to `[]const T`, and `&[_]T{...}` to `[]const T`.
- `s[i]` reads the header once and checks the index against the length: out of range traps `index out of bounds`, the same as `a[i]` on arrays (#6247). The interpreter and the JIT agree on every trap site. Indexing `str` is now supported, and a constant index into a literal folds.
- `x[i..j]` and `x[i..]` on an array, a pointer to an array, a slice or a str check `i <= j <= len`. Constants are checked at compile time; anything else traps at run time. Element writes go through `[]T`, never through `[]const T`.
- `t27b corpus specs` (macOS arm64): before, 161 pass (931 tests), 278 pass_vacuous, 2 fail, 764 rejected, 0 mismatch. After, 162 pass (938 tests), 278 pass_vacuous, 2 fail (same two files), 763 rejected, 0 mismatch. The new pass is validation_engine.t27, and the reference passes it 7/7.
- Honest result: `type []T` dropped from first blocker in 136 files to 0. But those files now stop on the next blocker (f32 42, BenchBlock 22, f64 12, ?T 6, and more), so only one more file passes in full.
- The reference Zig backend has bugs on both forms: it writes `x[i..]` as `x[i]` and `&[_]T{}` as `&.{ _ }`.
- Tests: cli/t27b/tests/source.rs adds slice-of-array, write-through, str, literal and field tests. It also adds three out-of-bounds traps (index, end, start) and precise rejections.
