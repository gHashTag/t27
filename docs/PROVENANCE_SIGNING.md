# Provenance and Signing — T27 Artifact Traceability

**Status:** Active (Ring 055)
**Date:** 2026-05-09
**Purpose:** Define provenance tracking and code signing strategy for T27 artifacts

---

## 1. Overview

This document defines the strategy for tracking provenance and signing T27 artifacts to ensure reproducibility, integrity, and trust.

### 1.1 Goals

1. **Reproducibility** — Every artifact can be reproduced from source
2. **Integrity** — Every artifact's integrity can be verified
3. **Traceability** — Every artifact can be traced to its source commit
4. **Trust** — Artifacts can be verified by third parties

### 1.2 In-Scope Artifacts

| Artifact Type | Current Status | Signing Status |
|---------------|----------------|----------------|
| Generated code (gen/*) | Tracked via git | Not signed |
| Conformance vectors | Tracked via git | Not signed |
| Binary releases (t27c) | Generated on release | Not signed |
| Zenodo deposits | DOI tracked | Signed by Zenodo |
| PyPI packages | Signed via Trusted Publishers | ✅ Signed |
| npm packages | Signed via npm token | ✅ Signed |
| crates.io packages | Signed via cargo token | ✅ Signed |

## 2. Current Provenance

### 2.1 Generated Code Provenance

Generated files include headers with provenance information:

```
// AUTO-GENERATED by t27c from spec: specs/numeric/gf16.t27
// DO NOT EDIT — changes will be overwritten
// Generated: 2026-05-09T22:00:00Z
// Commit: a1b2c3d4e5f6...
// Backend: Zig
// Schema Version: 1.0
```

**Verification:**
```bash
# Check header consistency
./scripts/tri validate-gen-headers
```

### 2.2 Conformance Vector Provenance

Conformance vectors include schema version and generation metadata:

```json
{
  "schema_version": "1.0",
  "spec": "specs/numeric/gf16.t27",
  "generated": "2026-05-09T22:00:00Z",
  "commit": "a1b2c3d4e5f6...",
  "tests": [...]
}
```

**Verification:**
```bash
# Validate schema
./scripts/tri validate-conformance
```

### 2.3 Release Provenance

GitHub releases include:
- Source code archive (tagged commit)
- Release notes
- Linked Zenodo DOI

**Verification:**
```bash
# Verify release tag
git verify-tag v0.1.0

# Check Zenodo DOI
curl https://doi.org/10.5281/zenodo.19456875
```

## 4. SBOM (Software Bill of Materials)

### 4.1 Current Status

SBOM generation is implemented in `release.yml`:

```yaml
- name: Generate SBOM (Software Bill of Materials)
  run: |
    cargo install cargo-cyclonedx
    cd bootstrap
    cargo cyclonedx --format json --output ../../sbom-bootstrap.json
```

### 4.2 SBOM Format

SBOMs are generated in CycloneDX JSON format:

```json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.4",
  "version": 1,
  "metadata": {
    "timestamp": "2026-05-09T22:00:00Z",
    "component": {
      "name": "t27-bootstrap",
      "version": "0.1.0",
      "type": "library",
      "purl": "pkg:cargo/t27-bootstrap@0.1.0"
    }
  },
  "components": [...]
}
```

### 4.3 SBOM Verification

```bash
# Verify SBOM
cargo cyclonedx verify --input-file sbom-bootstrap.json

# Validate SBOM schema
cyclonedx validate --input-file sbom-bootstrap.json
```

## 5. Seal Verification

### 5.1 Current Seals

Seals are SHA-256 hashes stored in `.trinity/seals/`:

```json
{
  "spec": "specs/numeric/gf16.t27",
  "seal": "a1b2c3d4e5f6...",
  "timestamp": "2026-05-09T22:00:00Z",
  "commit": "a1b2c3d4e5f6..."
}
```

### 5.2 Seal Verification

```bash
# Verify a seal
./scripts/tri seal specs/numeric/gf16.t27 --verify

# Verify all seals
./scripts/tri verify-seal-coverage
```

### 5.3 Seal Integrity

Seals provide integrity verification for:
- Spec files
- Generated code
- Conformance vectors
- Test results

### 7.1 Current Gaps

| Gap | Impact | Priority | Mitigation |
|-----|--------|----------|------------|
| No GPG signing of binaries | Medium | P1 | Implement in Q3 2026 |
| No signing of generated code | Low | P2 | Use git commits |
| No signing of conformance vectors | Low | P2 | Use seals |

### 7.2 Proposed Improvements

#### P1: GPG Signing of Binaries

1. Generate GPG key for releases
2. Sign binary releases with GPG
3. Upload public key to keyserver
4. Document verification process

```bash
# Sign release
gpg --detach-sign --armor t27c-linux-x86_64

# Verify signature
gpg --verify t27c-linux-x86_64.asc t27c-linux-x86_64
```

#### P2: Provenance Metadata

Add provenance metadata to all generated artifacts:

```json
{
  "artifact": "types.zig",
  "generator": "t27c",
  "generator_version": "0.1.0",
  "source_spec": "specs/base/types.t27",
  "source_commit": "a1b2c3d4e5f6...",
  "generated_at": "2026-05-09T22:00:00Z",
  "hash_sha256": "..."
}
```

#### P3: SLSA Provenance

Implement SLSA (Supply-chain Levels for Software Artifacts) provenance:

```bash
# Generate SLSA provenance
slsa-generator generate \
  --source github.com/gHashTag/t27 \
  --commit a1b2c3d4e5f6 \
  --artifact t27c-linux-x86_64 \
  --output provenance.json
```

## 8. Third-Party Verification

### 8.1 Zenodo Verification

Zenodo provides:
- Persistent DOI
- Content hash verification
- Timestamp
- Archival storage

**Verification:**
```bash
# Verify Zenodo DOI
curl -L https://doi.org/10.5281/zenodo.19456875

# Verify content hash
sha256sum t27-v0.1.0.tar.gz
# Compare with Zenodo checksum
```

### 8.2 Package Registry Verification

Each package registry provides verification:

**PyPI:**
```bash
pip install golden-float
pip show golden-float
# Verify hash
```

**npm:**
```bash
npm install golden-float
npm info golden-float
# Verify integrity
```

**crates.io:**
```bash
cargo install golden-float-ffi
cargo search golden-float
# Verify version
```

## 9. Security Considerations

### 9.1 Key Management

- Release keys stored in GitHub Secrets
- Rotation quarterly
- Backup keys offline
- Document key handoff

### 9.2 Signing Security

- Use hardware security modules (HSM) if available
- Separate signing keys for different artifacts
- Monitor key usage
- Revoke compromised keys immediately

### 9.3 Provenance Security

- Verify provenance before using artifacts
- Check for tampering
- Verify chain of trust
- Report suspicious activity
