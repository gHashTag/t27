## Where it ran

Both runs used the Railway t27b lab, an x86_64 machine (AMD EPYC 9655, 48 cores) shared with other work. The source was master `be9757784`, plus the five-line `TIME <test> <ns>` print this PR adds to `t27b test --time`. That print does not change code generation.

Every program ran as aarch64 code under `qemu-aarch64` 7.2 in user mode. Run times are therefore emulated arm64 time. They are comparable across rows, but they are not native speed.

Nothing ran on the Mac.

The six kernels are `specs/benchmarks/kernel_{fib,sieve,matmul,collatz,ternary,f64loop}.t27` (#6568), the same six as the #6488 comment.

## C6: warmup (Barrett et al., OOPSLA 2017, DOI 10.1145/3133876)

**Setup.** Each kernel got a file of 500 identical tests. t27b compiles the file once and runs the tests in order in one JIT image, so test *i* is in-process iteration *i*. Each kernel ran in 10 process executions, interleaved with the other kernels, between 10:23Z and 10:39Z. Every iteration checks its oracle, and all 60 executions passed 500 of 500.

**Classifier.** The method is the paper's, scaled from 2000 iterations to 500. `warmup.t27` sets out the scaling and every step:

- **Outliers.** The window is 50 iterations. A point is an outlier if it lies outside the median +/- 3 x (p90 - p10).
- **Changepoints.** Optimal partitioning with a mean-and-variance cost and a penalty of 15*ln(n). This gives the same segments as PELT (Killick et al. 2012).
- **Steady state.** The paper's rule with DELTA = 1 ms and a final 125 iterations.
- **Per-benchmark class.** Each benchmark gets a class over its 10 executions.

**Results:**

| Kernel | Class | Executions | Steady-state median |
|---|---|---|---|
| sieve | FLAT | 10 flat | 22.2 ms |
| collatz | FLAT | 10 flat | 27.5 ms |
| ternary | FLAT | 10 flat | 27.6 ms |
| fib | GOOD INCONSISTENT | 9 flat; 1 warmup (run 08, steady from iteration 36) | 32.1 ms |
| matmul | GOOD INCONSISTENT | 9 flat; 1 warmup (run 04, steady from iteration 8) | 41.7 ms |
| f64loop | BAD INCONSISTENT | 9 flat; 1 no steady state (run 10: a shift from 33.5 to 44.0 ms at iteration 426) | 34.0 ms |

**Reading the results:**

- **First iteration.** No kernel has a first-iteration spike. The median over executions of iteration 1 divided by the mean of iterations 101 to 500 is 0.90 to 1.03. That fits a JIT that compiles every function once, before the first test, with no tiers.
- **f64loop.** The late shift in f64loop run 10 is read as lab load. It is not verified.

**Caveats:**

- qemu translates code on first execution, so an early slow iteration could be qemu's warmup and not t27b's.
- The lab load average was 21 to 88 during the run.
- The run used 500 iterations, not 2000.
- The benchmarks are these six kernels, not every `bench` block in the corpus.
- The issue asked for native arm64. This run is emulated.

## C7: compile speed and code quality

**Method.** The same method as the #6488 comment: 5 repetitions per row, minimum and median published, and the load average recorded with every sample. The run went from 11:32Z to 11:50Z. All 420 timed builds and runs that report an exit code exited 0.

**Rows:**

- **t27b JIT.** Two numbers: the process wall time, and the run phase from `--time`.
- **t27c gen-c.** The C output is compiled two ways:
  - with `aarch64-linux-gnu-gcc` 12.2, at -O0 and -O2;
  - with clang 21.1.0 as shipped in zig 0.16.0 (`zig cc`, musl target), at -O0 and -O2. The lab has no standalone clang.
- **t27c gen.** The Zig output is built with `zig test` in Debug and ReleaseFast.

**Compile times.** Compile rows are timed on the x86 host. The exception is the t27b JIT compile, which is the sum of its phases before `run`, under qemu.

**Geometric means of the median ratios:**

**Caveats:**

- Everything runs under qemu.
- clang -O2 on f64loop is read as folded at compile time. This was not checked by disassembly.
- The zig compile rows include building the test runner with a fresh local cache. libc and compiler_rt come from a warmed global cache.
- The t27b JIT compile time is emulated, so it is not 1:1 with the x86 compile rows.

## Known defect found on the way

When a `.t27` file that imports with `use` ends in `endmodule`, the spliced source t27c's `use` resolution writes fails to compile. t27c then falls back to the unspliced original ("spliced source did not compile"), and the result is "use of undeclared identifier".

Measured on the lab: the same importer passed without the `endmodule` line and was blocked with it. Where the splice puts the declarations was not inspected.

`warmup_t27b.t27` therefore has no `endmodule`.
