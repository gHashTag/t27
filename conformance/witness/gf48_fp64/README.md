## Why FP64 (not FP32)

Phase-A formats (gf4..gf32) decode into IEEE binary32 (23-bit mantissa). gf48 has
M=29, which does NOT fit in FP32 but fits EXACTLY in FP64 (52 bits). So the target
type is binary64, and the entire wide normal range decodes WITHOUT mantissa
rounding (M=29 <= 52). Rounding appears only on the FP64-subnormal path (deep
underflow, true_exp < -1022), handled by gradual underflow + RNE with guard/sticky.

3. **FP64 fixed-width RTL bit-model** -- `rtl_bit_model_fp64.py`
   Python model of `gf_decode_param_fp64.v` with explicit width masks

   infeasible):
   ```
   cd conformance/witness/gf48_fp64 && python3 rtl_bit_model_fp64.py
   ```
   Expected: `224255/224255 bit-exact (fails=0)`.

## Independent iverilog witness (for the local agent)

The strongest witness is an independent iverilog simulation using
`gf_decode_param_fp64.v` (DUT) against golden vectors generated by the Fraction
oracle. Lesson 04.07 (twice-confirmed): Python arbitrary-width int does NOT catch
fixed-width bugs (truncation / OOB-read); only an iverilog run is the true
independent second decoder for the RTL. This has NOT yet been run in this sandbox
(no iverilog here). The local agent runs:

```
cd conformance/witness/gf48_fp64
python3 gen_vectors_fp64.py vectors_gf48.txt        # 224255 vectors from golden oracle
iverilog -o dut gf_decode_param_fp64.v tb_gf_decode_fp64.v
vvp dut
```

Expected canonical line (grep target):
```
HW RESULT: 224255/224255 bit-exact (fails=0)
gf48 FP64 iverilog witness: PASS
```

Note: this is a SIMULATION witness, not on-silicon Tier-E.
