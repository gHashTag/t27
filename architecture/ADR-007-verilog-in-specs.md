# ADR: Расхождение де-юре/де-факто по generated `.v` в `specs/` (Closes #1435, Refs #960 #1205)

- **Статус:** предложено (черновик Wave-лупа 2026-07-06g)
- **Репозиторий:** `gHashTag/t27`, HEAD `6c704801` (master)
- **Закон конституции:** L2 GENERATION (`docs/T27-CONSTITUTION.md`) — «Files under `gen/` are generated; edit the `.t27` spec instead», проверка `t27c validate-gen-headers`.

## Контекст (факты, [доказано])

Issue [#960](https://github.com/gHashTag/t27/issues/960) («W84 R-SPECS: L2 violation — generated Verilog files in specs/») и дочерний [#1205](https://github.com/gHashTag/t27/issues/1205) («migrate remaining generated .v files from specs/ to gen/») **закрыты** как выполненные.

Прямой факт-чек на HEAD `6c704801` (`gh api repos/gHashTag/t27/git/trees/master?recursive=1`):

| Путь | Число файлов `.v` |
|---|---|
| `specs/**/*.v` | **61** |
| `gen/**/*.v` | **33** |

Тело самого #1205 гласит: «**Status:** 30/61 files already migrated. ~30 remain» + acceptance-criteria (identify / move / regenerate seals / suite passes) с **НЕотмеченными** галочками. При этом issue закрыт.

Проверка конкретного файла `specs/fpga/uart.v` — заголовок:
```
// Generated from t27 spec: ZeroDSP_UART
// DO NOT EDIT - generated by t27c gen-verilog
```
То есть это **сгенерированный** артефакт. Одновременно уже существует канонический `gen/verilog/fpga/uart.v` → `specs/fpga/uart.v` = дубликат-фантом, оставшийся после частичной миграции.

## Проблема

Расхождение де-юре/де-факто: issue закрыт («Fixed»), но артефакт нарушения (61 generated `.v` в `specs/`, часть уже продублирована в `gen/`) присутствует на HEAD. Это:
1. нарушает L2 GENERATION [действующая норма проекта];
2. повторяет системный паттерн преждевременного закрытия issue по текстовому заявлению, а не по состоянию HEAD (тот же класс, что ранее наблюдался в trinity-fpga);
3. создаёт риск рассинхрона: правки в `specs/*.v` (которые «DO NOT EDIT») будут потеряны при регенерации.

## Развилка решений

**Вариант A — доперенести (рекомендуется, если файлы действительно генерируемые).**
- Удалить 61 `.v` из `specs/` (те, что дублируются в `gen/`, — удалить; те, что ещё не сгенерированы в `gen/`, — прогнать `t27c gen-verilog` и положить в `gen/verilog/…`).
- Перегенерировать seals, прогнать suite.
- Переоткрыть #1205 до фактического прохождения acceptance-criteria ИЛИ открыть новый issue со ссылкой на этот ADR.

**Вариант B — узаконить как эталонные фикстуры конформанса.**
- Если часть `specs/**/*.v` — это осознанно зафиксированные golden-фикстуры (эталон для diff при регенерации), а не «живой» generated-код, — внести исключение в L2: явный whitelist-путь (напр. `specs/**/fixtures/*.v`) + пометка в конституции, что эти файлы иммутабельны и не подпадают под GENERATION-закон.
- Переместить их в отчётливо помеченную поддиректорию (`specs/**/golden/`), чтобы `validate-gen-headers` их не считал нарушением.

## Что предлагается PR этого лупа

Только **документ** (этот ADR) + переформулировка issue — без автоматического удаления 61 файла (это решение владельца: A или B). PR:
- добавляет `architecture/architecture/ADR-007-verilog-in-specs.md` (этот файл);
- в теле PR: `Refs #960 #1205`, ссылка на факт-чек;
- НЕ трогает SSOT (83 формата), не удаляет спеки.
